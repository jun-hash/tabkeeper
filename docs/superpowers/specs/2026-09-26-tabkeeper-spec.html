tabkeeper — 에이전트 탭 자동 아카이브

Spec · 2026-09-26 · author: jun-hash (+ Claude) · 사용자 지시로 브레인스토밍 게이트 이후 자율 구현, 구현 결과 기준으로 작성(as-built)

0. Overview 🟢

Problem

Orca·cmux 같은 에이전트 터미널에 병렬 에이전트를 돌리면 며칠째 안 쓰는 워크트리/탭이 사이드바에 쌓인다. 두 앱 모두 자동 정리 기능이 없고(Orca는 수동 cleanup UI만, cmux는 닫기만), 앱마다 API가 달라 한 번 만든 도구를 다른 앱에 옮기기 어렵다.

Goal

idle한 세션·워크스페이스를 계층적으로 자동 아카이브하고, 에이전트 대화까지 복원 가능하게 하는 호스트-독립 오픈소스 CLI/라이브러리.

Out of scope

  • 앱 내부 UI 패치(사이드바 버튼 등) — 외부 CLI/소켓만 사용
  • 실행 중 프로세스 상태(L4) 복원 — 대신 busy로 보호
  • 상주 데몬/이벤트 구독 — 스케줄러(launchd/cron)가 sweep를 주기 실행
  • 기본값에서의 워크트리 삭제 — purge는 옵트인

1. Requirements 🟢

  • US-1. 에이전트 여러 개를 돌리는 개발자로서, 안 쓰는 탭이 자동으로 정리되길 원한다 — 사이드바가 지금 하는 일만 보이도록.
  • US-2. 정리된 탭을 대화 맥락째 되살리고 싶다 — 아카이브가 두렵지 않도록.
  • US-3. 새 터미널 앱에도 파일 하나로 붙이고 싶다 — 오픈소스로 어디든 이식.
#GivenWhenThen
AC-1탭이 12h 무활동sweep스냅샷 저장 후 그 탭만 닫힘
AC-2워크스페이스의 모든 탭이 7d 무활동sweep워크스페이스 통째 아카이브(캐스케이드)
AC-3에이전트가 workingsweep탭·부모 워크스페이스 모두 유지
AC-4아카이브된 에이전트 탭restore같은 cwd·제목 + claude --resume <id>로 재생성
AC-5새 호스트plugin 모듈 등록코어 수정 없이 동작 (tmux 예제로 검증)
AC-6purge.enabled, 30d 경과sweep/purgeclean·pushed인 워크트리만 삭제

2. Business Logic & Policy 🟢

순수 함수 plan(workspaces, policy, now) → { actions, kept } (src/domain/policy.ts). I/O 없음.

순서규칙결과
1pinned 또는 protect.paths/titles 매칭 워크스페이스서브트리 전체 skip (pinned/protected)
2workspace idle = max(ws 활동, 모든 세션 활동) ≥ workspaceIdleblocker(permanent·focused·busy 세션) 없으면 archive-workspace, 있으면 kept 후 3으로
3세션 idle ≥ sessionIdle, 활동시각 모름이면 activity-unknownbusy·focused·protected title이면 kept, 아니면 후보
4살아남는 워크스페이스의 세션이 전부 후보가장 최근 세션 하나는 last-session으로 유지

불변식 (Global Constraints)

  • 닫기 전에 항상 레코드 저장(snapshot-before-close).
  • 레코드는 실제로 닫힌 것만 가리킨다: 닫기/아카이브 실패 → 레코드 삭제, 단 어댑터가 PartialArchiveError(일부 이미 닫힘)를 던지면 레코드 유지.
  • 워크스페이스 캐스케이드는 세션 보호를 상속: busy·focused·protected·activity-unknown 세션이 하나라도 있으면 워크스페이스 통째 아카이브 금지.
  • workspaceIdle ≥ sessionIdle (config 검증).
  • sweep·restore·purge는 배타 lock(link(2)로 원자 게시, 죽은 pid면 동일 pid 재확인 후 회수). dry-run은 호스트도 ledger도 변경하지 않음.
  • purge는 removeWorkspace 구현 + 워크스페이스가 다시 살아있지 않음(inventory 확인) + git guard(uncommitted·untracked/stash/no-upstream/unpushed) 모두 통과해야만. ignored 파일은 삭제됨.

4. Architecture 🟢

의존은 안쪽으로만: domain ← app ← (ports) ← infra/adapters. src/cli/app.ts만 모든 구현체를 안다.

Facade파일책임
SweepService.runsrc/app/sweep.tsprobe → inventory → observe → plan → snapshot → close
RestoreService.runsrc/app/restore.tsid prefix 해석 → adapter.restore → status 갱신
PurgeService.runsrc/app/purge.tsgrace 경과 + guard 통과 → removeWorkspace
HostAdaptersrc/ports/host-adapter.ts호스트 1개의 전체 경계

5. Seams 🟢

app → HostAdapter

가장 중요한 경계. 새 호스트 = 이 인터페이스 하나.

call-site
const workspaces = await adapter.inventory()
const mode = await adapter.archiveWorkspace(workspace)   // 'native' | 'closed'
await adapter.restore(record.workspace, record.mode === 'closed' ? specs : [])
frozen signature
probe(): Promise<Availability>
inventory(): Promise<readonly WorkspaceState[]>
readScrollback(ws, session, lines): Promise<string | undefined>

archiveWorkspace(ws): Promise<ArchiveMode>

removeWorkspace?(snapshot): Promise<void>
계약
  • payload: 정규화된 WorkspaceState/SessionState; ref는 코어에 불투명(어댑터가 핸들 인코딩)

  • 보장: 모르는 활동시각은 undefined(발명 금지), native는 호스트가 세션 재개를 보장할 때만

6. Contracts 🟢

SweepService.runIn {dryRun} · Out host별 HostReport(ok: planned/kept/archived/failures | unavailable | failed) · Pre config 유효 · Post archived의 모든 레코드는 store에 존재, dry-run이면 호스트 무변경 · Err lock 보유 중이면 StoreLockedError
RestoreService.runIn id 또는 유일 prefix · Out restored 레코드 · Err 없음/모호(RecordNotFound/Ambiguous), 이미 restored/purged, 호스트 비활성/미실행(RestoreError) · Post status=restored, restoredAt
PurgeService.runIn {afterMs, dryRun} · Out 레코드별 purged/would-purge/skipped(reason)/failed · Post purged만 status 변경
parseConfig기본값 병합(hosts는 기본 호스트와 merge), 모든 키 타입 검증, duration > 0, title regex 컴파일 가능

7. Core Flows 🟢

F1. Sweep

① 트리거

launchd/cron(기본 15m) 또는 수동 tabkeeper sweep

② 워크플로우

lock → 호스트별 probe → inventory → ObservedActivity(fingerprint→since) → plan → 각 action: capture(스크롤백 ∥ agent 탐지) → store.save → close/archive → report → (purge.enabled면) purge

③ 입력

호스트 CLI/소켓, Orca agent-hooks, cmux events.jsonl·sessions, ~/.claude/projects

④ 결정

전부 코드 결정론(plan). 외부/LLM 위임 없음 — 아카이브는 되돌릴 수 있어야 하고 설명 가능해야 하므로.

⑤ 에러

§3 참조. 호스트 단위 격리, action 단위 격리.

⑥ 결과

사이드바 정리 + ~/.local/share/tabkeeper/records/*.json

⑦ 연결

§5 HostAdapter, ArchiveStore, AgentLocator, ActivityLedger

F2. Restore

①

tabkeeper restore <id-prefix>

②

resolveRecord → status 확인 → probe → adapter.restore(snapshot, mode==='closed' ? specs : []) → status=restored

④ 결정

native면 호스트가 재개(Orca sleep의 세션 기억) — 중복 탭 방지. closed면 스냅샷 spec(title/cwd/url/resume command)으로 재생성.

⑤

워크스페이스가 사라졌으면: cmux/tmux는 재생성, Orca는 에러(워크트리 재생성은 사용자 몫)

F3. Observed activity (fingerprint)

②

어댑터가 화면 해시 제공 → ledger의 이전 해시와 같으면 since 유지, 다르면 now → lastActivityAt = max(호스트값, since)

④

첫 관측 시각부터 계산하므로 도입 직후엔 보수적(아무것도 idle 아님).

F4. Purge (opt-in)

②

archived·workspace·archivedAt ≤ now−after → capability 확인 → git guard → removeWorkspace(Orca: worktree rm, --force 없음) → status=purged

8. End-to-End 🟢

  1. tmux 격리 서버: stale(창1), proj(old, fresh) 생성 → old에 MARKER 출력 → 2.5s 대기 → fresh만 활동
  2. sweep → old 창(session 레코드) + stale 세션(workspace 레코드) 아카이브, 남은 창은 proj:fresh뿐
  3. old 레코드 스크롤백에 MARKER 존재
  4. 둘 다 restore → proj:fresh, proj:old, stale:lonely (원래 cwd)

자동화: test/e2e/tmux.e2e.test.ts. 실 Orca에는 read-only dry-run으로 검증(52건 판정, pinned/main 보호, 현재 세션 busy 인식).

10. Senior Review 🟢

10.1 워크스루

  1. 진입점: SweepService.run({dryRun}) 하나. 결과는 호스트별 리포트.
  2. 분리: 호스트 차이는 전부 HostAdapter 7개 메서드 뒤. 정책은 I/O 없는 plan().
  3. 흐름: inventory → observe → plan → snapshot-before-close.
  4. 계약: native vs closed 모드가 restore의 중복을 막는 핵심 계약.

10.2 Q&A

Q. Orca 내부 RPC(worktree.sleep)에 의존하는 건 위험하지 않나?

A. 먼저 archive 플래그(숨김)를 걸고 sleep은 best-effort. 런타임이 확실히 도달 불가일 때만 탭 닫기로 폴백하고 mode를 closed로 기록하므로 기능은 유지된다. 소켓은 close/전체 타임아웃에서 반드시 settle. RPC 존재는 잘못된 selector로 호출해 method_not_found가 아닌 selector_not_found를 받는 방식으로 무해하게 검증했다. 장기적으로 Orca에 worktree set --archived 업스트림 PR이 정답.

Q. 에이전트가 권한 프롬프트에서 대기 중이면?

A. busy가 아니다(Orca waiting, cmux needsInput). 대신 idle 임계값을 넘겨야만 아카이브되고 resume으로 대화가 복구되므로 손실이 없다. working/blocked/running만 보호한다.

Q. 모든 탭이 idle인데 워크스페이스가 permanent면 사이드바가 비지 않나?

A. last-session 규칙으로 가장 최근 탭 하나를 남긴다.

10.3 독립 리뷰 반영 (2026-09-26)

  • Orca RPC 무한대기 → close 핸들러 + 전체 타임아웃
  • 아카이브 실패 시 레코드 불일치 → 삭제/PartialArchiveError 규칙
  • 캐스케이드가 세션 보호 무시 → workspaceBlocker가 세션 보호 상속
  • purge가 재사용 중 워크트리 삭제 가능 → inventory 확인 + Orca는 ref 일치·isArchived 재확인
  • lock 경합 → link(2) 원자 게시, restore/purge도 lock
  • schedule 환경 유실 → config 절대경로 + 관련 env를 plist/cron에 고정
  • capabilities 중복 제거, 플러그인 계약을 ports/로 이동, 공개 API 보강
